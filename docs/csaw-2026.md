# Lancer l'agent sur la base officielle CSAW 2026

Les challenges de la compétition sont publiés dans
[NYU-LLM-CTF/CSAW26_LLMAC_DB](https://github.com/NYU-LLM-CTF/CSAW26_LLMAC_DB).

## Format de la base

- `dataset.json` : index `{identifiant: {year, event, category, challenge, path}}`,
  p. ex. `2026q-cry-polly` → `2026/CSAW-Quals/crypto/polly`.
- Chaque dossier contient un `challenge.json` : `name`, `category`, `description`, `flag`,
  `files` (fichiers remis aux joueurs), et pour les challenges à service : `compose: true`,
  `box`, `internal_port`, `proto` (`http` ou `nc`). La description contient `{box}` et `{port}`,
  remplacés à l'ingestion.
- 23 challenges en 2026 : crypto 4, forensics 4, misc 3, pwn 3, rev 3, web 6.
  11 ne demandent que des fichiers ; 12 demandent un service lancé par `docker compose`.

## Ce que l'agent voit, et ce qu'il ne voit jamais

Les dossiers de la base contiennent aussi les solutions des organisateurs (`solution/`,
`solve.py`, `writeup.md`, `flag.txt`...). Le règlement interdit de s'en servir. L'ingestion
(`csaw_agent/challenge.py`) suit donc deux règles :

1. Seuls les fichiers listés dans `files` sont copiés dans l'espace de travail du run ; le reste
   du dossier n'est jamais lu.
2. Défense en profondeur : un fichier listé dont le chemin ressemble à une solution, à un
   write-up ou au flag est écarté, et ce choix est écrit dans la trace (`excluded`).

Le flag du `challenge.json` part seulement dans le vérificateur, qui ne rend qu'un booléen.
La description et les fichiers restent des données non fiables, encadrées avant d'aller au LLM
(chapitre 4 : injection de prompt).

## Shell en bac à sable (`--shell`)

Le premier essai (qwen2.5:7b) a montré que le modèle réclame un shell : 23 appels à `nc`,
`grep`, `sqlite3`, `objdump`... L'option `--shell` lui en donne un, borné par le code et non par
la bonne volonté du LLM, puisque ses commandes dérivent de données non fiables :

- utilisateur `ctfsandbox` sans privilèges (`setpriv`), dossier de travail = fichiers du challenge ;
- clone de la base rendu illisible (`chmod 700`), et vérifié avant le premier challenge ;
- pas de réseau : `unshare -n` ; sinon espace de noms utilisateur (`unshare -rn`) ; sinon, comme
  sur Kaggle où les deux sont interdits, filtre seccomp qui refuse toute socket autre qu'AF_UNIX
  (et io_uring), sans aucun privilège. Le mode retenu est écrit dans la trace et le rapport ;
- délai maximal (120 s), environnement vidé, sortie tronquée ;
- garde-fou textuel contre `git`, `curl`, `pip`... (signalement précoce, pas une barrière).

Il faut lancer l'agent en root et créer l'utilisateur : `useradd -M -s /bin/bash ctfsandbox`.
Le notebook le fait, et installe `file`, `binutils`, `7z`, `sqlite3`, `tshark`, `exiftool`, `sox`.

## Challenges à serveur (`--docker`)

Les 12 challenges à service exposent un `docker-compose.yml` : le service se rattache au réseau
externe `ctfnet` et `expose` un port interne. L'option `--docker` démarre ce conteneur pour
chaque challenge à serveur, publie son port sur `127.0.0.1`, et donne à l'agent un outil réseau
**borné à ce seul service** :

- `http` pour `proto: http` : requêtes GET/POST, en-têtes, cookies de session gardés entre appels,
  redirections suivies. L'outil ne prend jamais d'hôte en argument, seulement un chemin.
- `connect` pour `proto: nc` : dialogue TCP brut (envoi d'octets, `\n` et `\xNN` interprétés),
  connexion gardée ouverte. Utile pour pwn et crypto.

Le shell en bac à sable, lui, reste sans réseau : seules ces deux portes typées sortent, et elles
ne mènent qu'au challenge. Impossible, même sous injection de prompt, de télécharger une solution.
Le conteneur est arrêté et supprimé à la fin du challenge, et la base reste intacte (on n'écrit
qu'un fichier de surcharge temporaire pour publier le port).

Docker n'existe ni sur Kaggle ni sur Colab. On lance donc ces challenges là où Docker est présent :
**GitHub Actions** (gratuit sur un dépôt public, voir `.github/workflows/csaw.yml`), un PC, ou
Codespaces. Sans Docker, `--docker` est ignoré et les challenges à serveur sont notés
`ignore_serveur`.

## Commandes

```bash
git clone --depth 1 https://github.com/NYU-LLM-CTF/CSAW26_LLMAC_DB.git
python -m csaw_agent list CSAW26_LLMAC_DB/dataset.json
python -m csaw_agent run-all CSAW26_LLMAC_DB/dataset.json --skip-server --model ollama:qwen2.5:7b
sudo python -m csaw_agent run-all CSAW26_LLMAC_DB/dataset.json --skip-server --shell --model ...
# Challenges à serveur (Docker requis) ; la clé du modèle vient de CSAW_API_KEY :
sudo -E python -m csaw_agent run-all CSAW26_LLMAC_DB/dataset.json --shell --docker \
    --model gemini:gemini-3.8-flash
python -m csaw_agent run-all CSAW26_LLMAC_DB/dataset.json --only 2026q-web-low_tide --docker --model ...
```

`--skip-server` note `ignore_serveur` dans `bilan.json` pour les challenges à service, sans les
lancer. Sur Kaggle ou Colab (sans Docker), le notebook fait tout cela pour les challenges à
fichiers (`CHALLENGES = "csaw"`).

## Routage multi-modèles (`--models`)

Aucun modèle gratuit n'est le meilleur partout : le raisonnement (crypto, rev) et le code
(pwn) ne demandent pas le même. Comme tous ces services parlent le protocole OpenAI, l'agent
peut en changer selon la catégorie du challenge, en une ligne. C'est un point de créativité (le
règlement note la créativité à 55 %), et cela tient dans les quotas gratuits.

```bash
python -m csaw_agent run-all CSAW26_LLMAC_DB/dataset.json --docker --shell \
  --models "crypto=openrouter:deepseek/deepseek-r1:free,\
rev=openrouter:deepseek/deepseek-r1:free,\
pwn=openrouter:moonshotai/kimi-k2.6:free,\
default=gemini:gemini-3.8-flash"
```

- Le modèle choisi pour chaque challenge est écrit dans la trace (événement `ingestion`).
- `--models` remplace `--model`. L'entrée `default=` est obligatoire.
- La clé de chaque fournisseur est lue dans `<FOURNISSEUR>_API_KEY` (p. ex. `OPENROUTER_API_KEY`,
  `GEMINI_API_KEY`, `GROQ_API_KEY`, `DEEPSEEK_API_KEY`, `CEREBRAS_API_KEY`), avec repli sur
  `CSAW_API_KEY` quand il n'y a qu'un fournisseur. Les clés ne sont jamais écrites dans la trace.
- Préréglages connus : `gemini`, `openrouter`, `groq`, `cerebras`, `deepseek`, `ollama`, `vllm`.

## Sur GitHub Actions

Le workflow `essai csaw` (`.github/workflows/csaw.yml`) se lance à la main (onglet *Actions* →
*essai csaw* → *Run workflow*). Il clone la base, installe les outils, démarre les conteneurs avec
Docker et publie les traces en artefact `runs`. La clé du modèle est le secret `GEMINI_API_KEY`
(*Settings* → *Secrets and variables* → *Actions*), passée à l'agent via `CSAW_API_KEY` et jamais
écrite dans la trace.

## Limites actuelles

- Sans `--shell`, pas d'outils pour les binaires, les pcap ou l'audio ; avec, ceux du système.
- Les challenges pwn demandent souvent un exploit construit pas à pas : `connect` donne le canal,
  mais la réussite dépend de la force du modèle.
