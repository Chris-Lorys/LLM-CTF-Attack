# Lancer l'agent sur la base officielle CSAW 2026

Les challenges de la compétition sont publiés dans
[NYU-LLM-CTF/CSAW26_LLMAC_DB](https://github.com/NYU-LLM-CTF/CSAW26_LLMAC_DB).

## Format de la base

- `dataset.json` : index `{identifiant: {year, event, category, challenge, path}}`,
  p. ex. `2026q-cry-polly` → `2026/CSAW-Quals/crypto/polly`.
- Chaque dossier contient un `challenge.json` : `name`, `category`, `description`, `flag`,
  `files` (fichiers remis aux joueurs), et pour les challenges à service : `compose: true`,
  `box`, `internal_port`, `proto` (`http` ou `nc`). La description contient `{box}` et `{port}`.
- 23 challenges en 2026 : crypto 4, forensics 4, misc 3, pwn 3, rev 3, web 6.
  11 ne demandent que des fichiers ; 12 demandent un service lancé par `docker compose`.

## Ce que l'agent voit, et ce qu'il ne voit jamais

Les dossiers de la base contiennent aussi les solutions des organisateurs (`solution/`,
`solve.py`, `writeup.md`, `flag.txt`...). Le règlement interdit de s'en servir. L'ingestion
(`csaw_agent/challenge.py`) suit donc deux règles :

1. Seuls les fichiers listés dans `files` sont copiés dans l'espace de travail du run ; le reste
   du dossier n'est jamais lu.
2. Défense en profondeur : un fichier listé dont le chemin ressemble à une solution, à un
   write-up ou au flag est écarté, et ce choix est écrit dans la trace (`excluded`).

Le flag du `challenge.json` part seulement dans le vérificateur, qui ne rend qu'un booléen.
La description et les fichiers restent des données non fiables, encadrées avant d'aller au LLM
(chapitre 4 : injection de prompt).

## Shell en bac à sable (`--shell`)

Le premier essai (qwen2.5:7b) a montré que le modèle réclame un shell : 23 appels à `nc`,
`grep`, `sqlite3`, `objdump`... L'option `--shell` lui en donne un, borné par le code et non par
la bonne volonté du LLM, puisque ses commandes dérivent de données non fiables :

- utilisateur `ctfsandbox` sans privilèges (`setpriv`), dossier de travail = fichiers du challenge ;
- clone de la base rendu illisible (`chmod 700`), et vérifié avant le premier challenge ;
- pas de réseau : `unshare -n` ; sinon espace de noms utilisateur (`unshare -rn`) ; sinon, comme
  sur Kaggle où les deux sont interdits, filtre seccomp qui refuse toute socket autre qu'AF_UNIX
  (et io_uring), sans aucun privilège. Le mode retenu est écrit dans la trace et le rapport ;
- délai maximal (120 s), environnement vidé, sortie tronquée ;
- garde-fou textuel contre `git`, `curl`, `pip`... (signalement précoce, pas une barrière).

Il faut lancer l'agent en root et créer l'utilisateur : `useradd -M -s /bin/bash ctfsandbox`.
Le notebook le fait, et installe `file`, `binutils`, `7z`, `sqlite3`, `tshark`, `exiftool`, `sox`.

## Commandes

```bash
git clone --depth 1 https://github.com/NYU-LLM-CTF/CSAW26_LLMAC_DB.git
python -m csaw_agent list CSAW26_LLMAC_DB/dataset.json
python -m csaw_agent run-all CSAW26_LLMAC_DB/dataset.json --skip-server --model ollama:qwen2.5:7b
sudo python -m csaw_agent run-all CSAW26_LLMAC_DB/dataset.json --skip-server --shell --model ...
python -m csaw_agent run-all CSAW26_LLMAC_DB/dataset.json --category crypto --model groq:<modèle>
python -m csaw_agent run-all CSAW26_LLMAC_DB/dataset.json --only 2026q-for-hemispheres --model ...
```

`--skip-server` note `ignore_serveur` dans `bilan.json` pour les challenges à service, sans les
lancer. Sur Kaggle ou Colab, le notebook fait tout cela tout seul (`CHALLENGES = "csaw"`).

## Limites actuelles

- Pas encore d'outil réseau (HTTP, `nc`) ni de bac à sable Docker : les 12 challenges à service
  ne peuvent pas être résolus. Kaggle et Colab n'ont pas Docker ; il faudra un PC avec Docker
  (le modèle pouvant rester sur une API gratuite) pour lancer les `docker-compose.yml`.
- Sans `--shell`, pas d'outils pour les binaires, les pcap ou l'audio ; avec, ceux du système.
